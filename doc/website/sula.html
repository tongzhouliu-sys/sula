SULA SALES BRIEF

OpenClaw 让 Agent 跑起来，
SULA 让企业把它们用起来

WHAT IS SULA

一句话说清楚：SULA 是 OpenClaw 的企业交付层

OpenClaw 解决“Agent 如何运行”；SULA 进一步解决“谁能用、该用谁、能访问什么、谁来审批、结果归谁、如何持续运营”。

FOUNDATION OpenClaw 原生能力

Agent、模型、工具、Skill、渠道、会话、任务与自动化运行。

＋
BUSINESS LAYER SULA 企业管理层

员工档案、组织用户、业务授权、审批、审计、成果与生命周期。

＝
BUSINESS OUTCOME 可规模化的数字团队

普通员工敢用，业务管理者会管，IT 与合规看得见、控得住。

S
客户购买的不是一个更漂亮的聊天框。

客户购买的是一套把分散 Agent 能力转化为岗位化服务、受控协作和可复用组织资产的方法与系统。

WHY SULA

企业从“Agent 能工作”走向“组织敢使用”，中间还差一层

原生 OpenClaw 的技术能力很完整；企业扩展到多用户、多部门和真实业务后，需要一套以组织和责任为中心的产品层。

01

从技术对象到业务岗位

普通员工不需要理解 Agent、Session、Tool 或 Gateway，只需要知道“这位数字同事负责什么、怎样委派、会交付什么”。

02

从能调用到可授权

企业需要按用户、部门、员工和具体资源控制可见与可操作范围，而不是把共享 Agent 等同于共享全部会话和成果。

03

从一次执行到员工生命周期

数字员工需要入职审核、岗位档案、负责人、发布、暂停、交接与归档，成为可以持续运营的组织角色。

04

从生成文件到组织资产

报告、表格和方案需要关联任务、来源、版本、审阅与下载记录，才能被安全复用并持续积累。

CEO / 管理层

看见数字劳动力

知道谁在岗、服务谁、完成什么，以及价值沉淀在哪里。

业务负责人

按岗位调度

用业务语言配置服务、分配员工、查看进度和接管异常。

IT / 安全

保留技术控制力

复用 OpenClaw，统一管理版本、权限、连接、密钥引用和审计。

一线员工

低门槛协作

像找同事一样选择数字员工，提交任务并接收可信成果。

SULA VS. OPENCLAW

不是能力重复，而是职责分层

原生 OpenClaw 是强大的个人 AI 助手与 Agent 运行平台；SULA 不重做这些能力，而是增加企业业务入口、组织治理和持续运营。

官方核心定位是运行在自有设备、连接多种渠道的个人 AI 助手，并通过 Gateway 统一运行与连接。		 企业业务层
企业数字员工管理系统，让长期业务 Agent 以员工身份进入组织。		 从“我有一个 AI 助手”升级为“企业有一支数字员工团队”。
主要对象 Gateway、Agent、Workspace、Session、Task、Skill、Tool、Plugin、Channel、Node。 企业、部门、用户、数字员工、岗位、授权关系、审批、成果与员工生命周期。 技术对象保留原样，业务用户看到的是自己熟悉的组织语言。
原生能力 已提供聊天、会话、任务、Skill、Cron、渠道、节点、执行审批与 Control UI 等丰富能力。 通过 Adapter 复用并映射原生能力，不重新实现 Agent Loop、工具执行或消息运行时。 既保留开源生态与快速迭代，又避免重复造轮子。
用户体验 Control UI 以 Agent、会话、配置和运行状态为中心，适合操作者与技术管理员。 员工工作台以姓名、岗位、服务说明、任务、进度和成果为中心，另设业务管理后台。 普通员工无需理解底层技术，培训与推广成本更低。
组织与身份 围绕 Gateway 身份、Agent、渠道发送者和会话组织运行。 建立企业用户、部门、角色、数据范围、员工负责人和用户—员工分配关系。 同一套 Agent 能力可以在企业内部按职责安全分发。
权限模型 提供 Gateway 认证、Scope、工具策略、沙箱、配对和原生审批等安全机制。 在原生安全之上增加 RBAC、条件策略及 Session、Task、Artifact、Approval 等资源级 ACL。 共享同一位数字员工，不代表共享全部会话、文件与审批。
员工治理 可创建、配置和运行多个 Agent，并管理其 Workspace、Skill 与会话。 将长期业务 Agent 映射为数字员工，增加待审核、发布、分配、暂停、交接、离职与归档流程。 Agent 不只是“存在”，而是有岗位、有负责人、有边界、有连续履历。
连接管理 通过 Channel、Plugin、MCP 等连接消息渠道、工具和外部系统。 统一呈现连接库存、归属、授权、健康、密钥引用和审计，并按 Driver 逐步开放写入。 企业知道“谁在用哪个账号、连接是否健康、发生过什么变更”。
成果管理 会话、任务和 Artifact 由原生运行能力产生并保存。 提供面向业务的成果中心，增加来源、版本、保留期、资源授权、下载审计和资产化索引。 一次交付不再散落在聊天里，而能成为下一次工作的可靠起点。
审计与运营 提供运行日志、健康检查、使用量、原生活动与诊断能力。 增加业务主体、策略判定、审批结果、前后差异、责任链、同步对账和运营指标。 管理层、业务、IT 与审计可以围绕同一条证据链协作。
典型客户 个人、单一操作者、技术团队、快速试验与需要高度可配置能力的场景。 需要多用户、多部门、岗位化服务、资源隔离、审批审计和成果运营的企业。 是否选择 SULA，关键看 AI 是否已经从“个人工具”进入“组织生产”。

销售结论：SULA 与 OpenClaw 不是替代关系。OpenClaw 是运行引擎和原生控制面；SULA 是企业用户入口、业务控制面与治理运营层。

BETTER TOGETHER

保留 OpenClaw 的速度，为企业增加一层秩序

SULA 通过服务端 Adapter 连接 OpenClaw Gateway。现有 Agent、Workspace、Skill、Session、Channel、MCP 与治理逻辑无需重新创建，门户负责发现、映射、授权和运营。

  • 技术资产不推倒重来：继续使用 OpenClaw 的生态、渠道与运行能力。
  • 普通用户不直面高权限控制面：企业用户通过 SULA 使用被授权的数字员工。
  • 升级边界清楚：原生状态以 OpenClaw 为准，组织与业务授权以 SULA 为准。
  • 能力按版本开放：通过能力探测与兼容矩阵，避免界面承诺底层不存在的功能。

WHEN TO CHOOSE

客户应该怎样选择

判断标准不是 Agent 数量，而是 AI 是否已经进入多人协作、业务授权和组织责任。

原生 OpenClaw 已足够

个人或单一操作者，先追求快速可用

适合技术驱动、信任边界简单、由少数管理员直接使用和维护的阶段。

  • 个人助手、开发者或技术团队内部使用
  • 主要由同一操作者配置 Agent、Skill 与渠道
  • 暂不需要企业用户、部门和资源级业务授权
  • 优先验证模型、工具、渠道和自动化效果
选择 SULA

多人、多部门，把 Agent 变成正式生产力

适合需要让业务员工规模化使用，同时保留权限、审批、审计和成果管理的企业。

  • 一个用户需要多位数字员工，或一位员工服务多人
  • 需要按岗位、部门、用户和资源设置访问边界
  • 需要数字员工入职、发布、交接、停用和归档
  • 需要高风险审批、成果追溯和企业资产沉淀

最有价值的客户通常不是“还没有 Agent”的企业，而是已经证明 Agent 有用、下一步需要让更多人安全使用并持续管理的企业。

LANDING PATH

从一位数字员工开始，建立可复制的企业样板

先把一个真实岗位做深、做稳、做出证据，再把能力扩展到更多团队。

  1. 盘点现有能力

    确认 OpenClaw 版本、Agent、Skill、连接、权限与真实业务需求，建立安全基线。

  2. 定义试点岗位

    选择高频、边界清晰、结果可审阅的流程，明确职责、输入、成果和人工节点。

  3. 建立使用闭环

    配置员工档案、用户授权、任务、成果与审计，在小范围真实业务中验证。

  4. 复制与运营

    将经过验证的岗位、能力和治理规则扩展到更多用户、部门与连接。

产品边界与表述说明

本页用于说明 SULA 的产品定位与目标能力。当前仓库中的门户文档状态为“立项与详细设计基线”，具体功能、连接写入范围和交付阶段以实际部署版本、能力探测结果及双方确认范围为准。SULA 不替代 OpenClaw Runtime，也不把门户业务权限宣称为主机级强隔离；不同外部客户或不可信域应使用独立 Gateway Cell。
